# Borrowed Hex — Decisions

Rulings made during implementation where the plan (`Docs/GAME_PLAN.md`) was silent,
ambiguous, or conflicted with what the project actually needed. Each entry records what was
decided, why, and what it costs if it turns out wrong.

| # | Phase | Decision | Why | Cost if wrong |
|---|---|---|---|---|
| D1 | 0 | Work directly on `main`, committing and pushing per phase | Explicit user instruction (overrides the plan's "no automatic commits") | None — user-directed |
| D2 | 0 | Combat simulation is plain C# (`ArenaSim`), MonoBehaviours only read input and draw views | Makes timing, capture, provenance and terminal ordering testable in EditMode and deterministic | Views need a sync layer; slightly more plumbing than component-per-entity |
| D3 | 0 | Collision is analytic on the XZ plane (swept circles vs circles/boxes), not PhysX | One consistent model, exact swept tests incl. initial overlap, cheap on WebGL; arena is flat boxes + circles anyway | Non-box obstacles would need new primitives |
| D4 | 0 | Unity "collision layers" are logical factions in code, not Unity physics layers | No PhysX collision is used, so physics layers would be unused configuration | None |
| D5 | 0 | `PlayerSettings.companyName = "BorrowedHex"` | Fixes the persistent save path identity before saves exist (section 12 check) | Changing it later moves Windows save location; migrate if renamed |
| D6 | 0 | Lit materials do not receive shadows; the sun casts none; characters get blob shadows | URP Lit shadow-receiving draws fail on WebGL (Chrome 152/ANGLE: "Mismatch between texture format and sampler type") and the arena rendered blank. Matches Unity forum report 863894 | Loses real cast shadows on the floor; revisit when final art/lighting arrives |
| D7 | 0 | Scene content is built by `ProjectBootstrap` (editor APIs, idempotent); runtime-only entities (player, enemies, projectiles, UI) are spawned in code rather than authored as prefabs | Keeps the CLI workflow repeatable and avoids hand-authored YAML; placeholder art is generated anyway | Artists replace views via `CharacterView`/view adapters rather than editing prefabs |
| D8 | 0 | The plan's phases are executed in order; each phase is one or more commits and a status entry in `IMPLEMENTATION_STATUS.md` instead of the superpowers task scripts | The plan uses "Phase N" sections, not the task-brief format the scripts parse | None |
| D9 | 1 | Dash and health live in the plain-C# sim (`PlayerMotor`, `ArenaSim.DamagePlayer`) instead of the plan's `DashController.cs`/`PlayerHealth.cs` components; `AimResolver` sits beside the input reader | Follows D2: one deterministic, EditMode-testable sim; the plan's file list is "proposed" | None functionally; file names differ from the brief |
| D10 | 1 | Focus loss also opens the pause menu (in addition to the FocusLost clock reason) | Regaining focus — often by clicking into the browser canvas — should not drop the player straight into live combat or turn that click into a catch | One extra click to resume after alt-tab |
| D11 | 1 | Sim runs at a fixed 60 Hz with frame time clamped to 0.1 s; views interpolate | Frame-rate-independent outcomes (dash distance, cooldowns) and smooth drawing on high-refresh displays; long hitches are dropped rather than replayed | Under 10 fps the game runs slower than real time |
| D12 | 2 | Hostile shots pass through an invulnerable player (dash or post-hit) instead of being consumed | Dashing through a volley becomes a readable skill; consuming shots on i-frames would silently delete ammunition the player may want to catch next | Volleys feel less dangerous; revisit if dash is too strong |
| D13 | 2 | Enemy health and damage are floats | The 15% perfect bonus and power multipliers on 1-damage bolts must accumulate rather than round away | HUD/achievement code must format, not compare, fractional values |
| D14 | 2 | Views poll sim state each frame; events only drive one-shot flourishes | A missed or duplicated event can never leave ghost sprites; restart simply destroys the view root | Small per-frame cost iterating lists (dozens of entries) |
| D15 | 3 | Capture is tested against the live aim every tick of the window, by sampling the swept segment (≤0.1 units) plus the exact impact time | Fast shots cannot skip the cone between ticks, and an exact capture/impact tie resolves by the capture < wall < actor order | Sampling could miss a sliver at a cone edge narrower than 0.1 units; acceptable at bolt radii |
| D16 | 3 | No "touching the body counts" capture: side or rear impacts during an open window still hurt | Section 2 requires the shot to be inside the cone; an earlier draft had a dead body-contact clause that, once fixed, would have made the cone meaningless at contact range | Catches feel stricter near the body; revisit only if playtests call it unfair |
| D17 | 3 | Aim updates before packet expiry each tick; expiry (step 3) precedes the catch (step 4) | Release follows the freshest aim, and a slot freed this tick can be used by a catch on the same tick | None known |
| D18 | 3 | HUD packet panels are listed oldest-first rather than pinned to a slot index | Equal lifetimes mean the oldest always fires first, so the leftmost bar is always "next"; pinned panels would leave a gap | Panels shift left when one releases |
| D19 | 3 | Plan's proposed files consolidated: `CaptureGeometry` lives in `CaptureController.cs`, `PacketStore` in `CapturedPacket.cs`, `ReleaseService` in `ArenaSim.Capture.cs`, the three test files in `CaptureTests.cs` (two fixtures) | Each piece is small and only meaningful beside its partner | A later split is a pure move |
| D20 | 4 | One `RangedCaster` brain parameterised by tuning instead of separate Acolyte/Scatter/Siege classes; Pursuer is its own brain | The three share the telegraph/aim-lock rhythm, so one fix reaches all of them; the plan prefers formations over new types | A future caster with genuinely different rules needs its own brain |
| D21 | 4 | Hostile rocket bursts are visual only; the incoming rocket deals its one player hit on contact | Section 4: incoming versions deal one player hit; area damage on the player would make a rocket worth more than that | Incoming rockets may feel weak; tune by speed or telegraph rather than area damage |
| D22 | 4 | Returned rockets deal all damage through the burst (direct damage 0) and never pierce | Guarantees each enemy is hit once per rocket, including the one it struck | Piercing upgrades do not apply to rockets |
| D23 | 4 | Explosions resolve instantly at impact instead of being scheduled | Nothing pending to cancel on death or restart; cannot double-trigger | No delayed-fuse rockets without revisiting |
| D24 | 4 | Lantern starvation ignores the lantern's own bolts in flight, but stored packets (including of lantern bolts) still end it | Otherwise every pair resets the 2 s timer and the cadence stretches to flight time + 2 s; packets are named explicitly by section 3 | None known |
| D25 | 4 | Pursuer damage comes only from its telegraphed strike, resolved once at the end of the wind-up; body contact is harmless | Every hit is readable and avoidable (section 4: clearly telegraph melee wind-up) | Crowding by pursuers costs space, not health |
| D26 | 4+ | Remove the arcane lantern; a melee-only remainder is answered by parrying Pursuer strikes (catch button, same cone and window) into a riposte at the attacker | Owner playtest: the lantern felt random and out of place. Parry keeps the one verb (borrow the enemy's attack) and makes melee enemies their own ammunition | Parry timing (0.25 s window in a 0.55 s wind-up) may be too strict for some players; tune `capture.window` or `pursuer.telegraph`. Plan section 3's starvation rule no longer exists |
| D27 | 4+ | The riposte flies at the attacker, not along the aim, and pierces one extra enemy | The cone is 90 degrees wide; along-aim would miss the attacker when parried at the cone edge. Pierce rewards parrying into a pack | Less aiming expression than an aimed riposte |
| D28 | 4+ | Parry ignores packet slots and capacity; it requires a strike that would actually hit (the "would hit" half superseded by D36) | The answer to a melee wave must work while holding ammunition; no free ripostes from strikes that would miss anyway | None known |
| D29 | 4+ | Riposte XP/score treatment: kills count normally through kill value; no separate capture XP | Phase 5/8 have not defined it yet | TBD: should a parry earn capture XP like a perfect catch? Owner question for Phase 8 |
| D30 | 4+ | Dev summon/auto-spawn/clear controls live in the sandbox dev panel only; the auto-spawn choice persists across Reset | Drilling one matchup should not be undone by every restart; scored runs never show the panel | None known |
| D31 | 4+ | Packets occupy a fixed slot index from capture to release; a new packet takes the lowest free index | Owner direction: a held slot is locked to what was captured; the capture rule was already one packet per catch window, so the change is making slot identity stable for selection | None known |
| D32 | 4+ | Right mouse releases the selected packet immediately, along the current aim, with no damage penalty | Owner direction: a faster pace. A penalty would make the 3 s timer the optimal play again | Early release may make packet timing trivial; a later upgrade can reward holding instead |
| D33 | 4+ | Q cycles the selection (wraps); right mouse fires ONLY the selected slot — an empty selected slot does nothing (revised: the first version fell back to the oldest packet); selection does not auto-move | Owner bug report: the fallback made Q look cosmetic, since RMB fired something either way. A binding selection makes the choice real | A dead click when the player forgets to switch; the HUD outline is the mitigation |
| D34 | 4+ | HUD packet panels pinned to slot index (supersedes D18) | With selection, a panel that slides left when the other fires would look like the selection jumped | None known |
| D35 | 4+ | `PlayerCommand.With*` return a copy instead of mutating the receiver | A builder called on a stored command made Catch permanently held (found in scripted play mode) | None |
| D36 | 4+ | Parry = the parry band (arc at 1.15 inside the cone, 0.12 wide; was 0.2) touches the strike circle's rim band (0.09 wide; was 0.15, both narrowed 0.6x by the owner after the third playtest) while the parry window (first 0.5x of the catch window) is open; tested in closed form (`ParryGeometry.BandsMeet`). A parry wins over damage; otherwise being inside the strike circle is a hit. Being inside is NOT required: the band can touch the near rim from just outside (a "spacing parry") | Owner direction: "make parrying more difficult", thin edge against thin edge, 0.5x window. The band sits at 1.15, not on the cone's 2.8 rim, because a 2.8 rim can only touch the strike while the player stands well outside it (agreed with the owner before building). The literal rule is "the edges meet", so the outside-touch case was kept rather than adding an unrequested "must be in danger" condition | TBD owner question: should a spacing parry from outside the strike (player 1.75-1.96 from its centre) count? If not, one condition in `ArenaSim.TryParry` plus flipping one pinned test |
| D37 | 4+ | Enemies route around pillars with a per-tick shortest path over padded pillar corners (`EnemySteering.Waypoint`), used by pursuer seek, the ranged "too far" approach and Scatter repositioning; no navmesh | Owner bug: pursuers pinned square-on behind a pillar (wall sliding has no sideways push there). Four convex pillars make a corner visibility graph exact and tiny; recomputed each tick, so nothing goes stale | New non-box obstacles would need their own corner sets; a crowded arena costs ~20-node Dijkstra per blocked enemy per tick |
| D38 | 5 | The Collector, per the owner: 50 health (was 120); four patterns in a fixed cycle - bolt stream, sweeping melee, fan volley, ground slam; no rocket attack. The two melee patterns are avoidable hazards and cannot be parried | Owner direction. Plan section 4 already says melee attacks are "avoidable hazards, not automatically stealable abilities"; the cycle alternates ranged and melee so a capturable volley is never more than one pattern away | TBD owner question: should the sweep or slam be parryable like a Pursuer strike? Today neither is |
| D39 | 5 | Boss ammunition tuned up so a zero-passive player can win: stream 12 shots at 0.12 s (was 8 at 0.14), fan 9 bolts at 12 degrees (was 7), repositioning capped at 1.0 s (was 1.3) | Plan section 4: "tune so a new character with no permanent skills can win within the short-mode boss window". With the first numbers a scripted catch-and-return bot ended the window with the boss on 15/50 | The bot is a lower bound with perfect reactions in some respects and none in others (see TEST_EVIDENCE); a human playtest is the real check |
| D40 | 5 | A riposte builds combo exactly like a released packet's first hit | A riposte is the parry's "release"; without this a melee-only wave could never raise the multiplier | Combo may climb faster than intended in Pursuer-heavy waves |
| D41 | 5 | The boss intro pauses the gameplay clock (PauseReason.BossIntro); the name banner holds 2.4 s of real time, then the fight starts and the banner fades for 0.6 s | The banner must not eat boss-window time, and the boss must not attack under it | None known |
| D42 | 5 | Upgrade transitions show a Continue button only ("ENCOUNTER n SURVIVED") until Phase 6 adds the cards | Plan Phase 5 deliverable explicitly allows it | None |
| D43 | 5 | The short run is the default mode on launch; the sandbox (dev panel) is one button away in the pause menu and on the results screen | Phase 5's deliverable is a beginning-to-end game; testers still need the sandbox for drills | TBD: Phase 7's main menu replaces this switch |
| D44 | 5 | Each encounter has an authored formation pool; the first formation of an encounter is its signature one, later picks are seeded and never repeat the last. While spawns wait on the 12-enemy cap, no new formation is queued | Readable escalation and seeded variety (section 6) without an unbounded backlog behind the cap | A long stall at the cap delays the next formation rather than stacking it |
| D45 | 5 | Terminal order inside one tick: death, then victory, then time expiry. Upgrade transitions and the boss intro are blocked once the run has ended | Plan Phase 5 check: player death takes precedence over a same-tick boss kill | None |
